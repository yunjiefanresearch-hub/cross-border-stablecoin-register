# Platform validation evidence

## What the repository proves locally

`python -m tools.verify` is the only aggregate verifier. A passing run writes
`artifacts/validation/verify-summary.json` and proves, for the active interpreter:

- the environment matches `constraints/runtime.txt` and `constraints/dev.txt`;
- committed generated outputs survive a first regeneration unchanged;
- a second complete regeneration is byte-identical;
- research outputs reproduce and agree with `dataset.json`;
- structural, semantic, negative, schema and documentation gates pass;
- two wheel builds have the same SHA-256 under `SOURCE_DATE_EPOCH`;
- a repository-external clean environment installs the wheel;
- all six AgenticFi tools work with Python warnings promoted to errors;
- the clean runtime has no dependency conflicts or known vulnerabilities;
- SBOM and licence inventory are produced.

## What requires external execution

A workflow file is not evidence that a workflow passed. The following claims remain
`unverified_external` until a real run produces its artifact:

| Claim | Required evidence |
|---|---|
| Linux Python 3.10, 3.11, 3.12 and 3.13 | One successful `CBSR canonical verification` run whose four `verify-python-*` jobs and `required-verification` job are green |
| Windows clean room | Successful `verify-windows-clean-room-python-3.12` job or a physical Windows 11 transcript generated by `setup_windows.ps1 -Recreate` |

Download and retain the Actions artifacts with the release record. Do not copy a
green badge or workflow declaration into a release manifest as a substitute for the
JSON summaries and logs.

## Local cross-version evidence

`LOCAL_LINUX_MATRIX.md` and `local-linux-matrix.json` aggregate four real local Linux runs of the
canonical verifier. The aggregator rejects an incomplete run, a constraint-digest mismatch or a
source-fingerprint mismatch, or a cross-version wheel-byte mismatch. The current R4 evidence covers
Python 3.10.20, 3.11.15, 3.12.13 and 3.13.14, each with 73 canonical steps and 332 reproduced artifacts.
This closes the local interpreter-compatibility gap while leaving
the GitHub-hosted and Windows-hosted claims explicitly external.

When an execution sandbox blocks advisory-network access, maintainers may set
`CBSR_OFFLINE_AUDIT_SNAPSHOT=docs/validation/pip-audit-snapshot-2026-08-20.json`. The verifier accepts
that snapshot only when its dependency-lock digest matches and it covers every installed package.
This is recorded as snapshot-backed evidence, never as a live audit. GitHub release CI must leave the
variable unset so `pip-audit --strict` queries the live service.

## GitHub configuration

After the first green run, configure the default-branch ruleset to require the stable
`required-verification` check. The matrix and Windows job remain dependencies of that
check, while its name stays stable across matrix expansion.
